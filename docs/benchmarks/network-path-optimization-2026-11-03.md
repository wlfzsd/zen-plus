# 网络路径深度优化与对比测试报告（2026-11-03）

> 目标：围绕用户体感的三个轴 —— **请求速度 / 下载速度 / 网络稳定性** —— 先测量、再改码，
> 每一项都给出可复现的对比数据；被否决的候选同样留证据。
> 版本：`upstream-chain` 分支，基线 HEAD `bb9b260`（v3.1.8/v3.2.0 部署态，二进制 `98B0851D`）。
> 测量台：`internal/proxy/zz_perfbench_test.go`（`ZEN_PERF=1` 门禁，默认跳过）。

---

## 0. 方法与纪律

**三臂对照**：所有测量都有一条"地板臂"（floor），Zen 的代价 = Zen 臂 − 地板臂。

| 臂 | 路径 | 作用 |
|---|---|---|
| `chain-only` | 客户端 → 上游代理（CONNECT）→ 源站 | 地板：与 Zen 走同一条上游、同一个源站 |
| `zen-h2` | 客户端 → **Zen（入站 h2）** → 上游 → 源站 | 生产主流路径（浏览器 h2） |
| `zen-h1` | 客户端 → **Zen（入站 h1）** → 上游 → 源站 | 对照：h1 镜像腿 |

**合成链路**（`perfChain`）：本机 HTTP CONNECT 代理，可注入单向延迟、可在 CONNECT 阶段挂死。
延迟模型按**飞行（flight）**而不是"每块都睡"：先把 2ms 窗口内到达的字节收成一个 burst，
再睡一次延迟转发 —— 因为真实链路会把背靠背写合并进同一个 RTT。**这一条是测量台自身
的校准**：最初的"每块都睡"模型曾把 Zen 的 h2 路径测成"多一个 RTT"，修正模型后该差异
消失（见 §2.1 的 RTT 记账），避免了把测量器缺陷当成优化对象。

**纪律**（沿用 2026-11-03 排查教训）：同轮交替、多轮取中位、单轮不下结论；
真实网络侧同一 URL 相邻请求间隔 ≥1.5s。

**复跑**

```powershell
cd zen-desktop
$env:ZEN_PERF="1"                                        # 打开测量台
$env:ZEN_PERF_RTT="100ms"                                # 链路单向延迟（默认 100ms）
go test ./internal/proxy -run 'TestPerf' -v -timeout 30m  # 全套合成链路测量

$env:ZEN_PERF_REAL="1"                                   # 真实网络（真实上游链）
go test ./internal/proxy -run 'TestPerfReal' -v -timeout 30m
```

## 1. 基线事实：Zen 的每请求代价已经接近地板

合成链路（单向 100ms ⇒ RTT ≈ 200ms），每臂 3 轮 × 60 次，共 180 样本：

| 臂 | p50 | p90 | p99 | 结论 |
|---|---|---|---|---|
| chain-only | **205.8ms** | 206.2ms | 207.2ms | 地板 |
| zen-h2 | **205.8ms** | 206.4ms | 207.2ms | +0.0ms |
| zen-h1 | 206.0ms | 206.6ms | 206.9ms | +0.2ms |

**每请求的单向传输次数记账**（同一轮，每臂 5 次）：

| 臂 | 请求向 | 响应向 | 平均 TTFB |
|---|---|---|---|
| chain-only | 1.00 次 / 44B | 1.00 次 / 991B | 205.8ms |
| zen-h2 | 1.00 次 / 72B | 1.00 次 / 991B | 206.0ms |
| zen-h1 | 1.00 次 / 130B | 1.00 次 / 1076B | 206.2ms |

→ **Zen 在热路径上没有额外 RTT**，TTFB 与"直接经上游"持平（差 <0.3ms，在噪声内）。

**大对象吞吐**（16MB，环回、链路无人工延迟，每臂 5 轮）：

| 臂 | p50 | min–max |
|---|---|---|
| chain-only | 43.3 MB/s | 34.3–58.0 |
| zen-h2 | **61.9 MB/s** | 38.9–63.0 |
| zen-h1 | 45.7 MB/s | 40.6–49.4 |

→ Zen 的数据面**没有吞吐回退**（h2 腿反而更快：批量读更大）。

**每字节堆分配**（16MB 下载期间 `TotalAlloc` 增量）：0.01x / 0.04x / 0.01x
→ "每个响应现分配 32KB 拷贝缓冲"实际摊销到整段传输上不到 1%，**池化没有价值**（见 §4.2）。

**并发**（32 worker，环回无延迟，1280 请求/臂）：

| 臂 | rps | p50 | p99 |
|---|---|---|---|
| chain-only | 26,003 | 1.03ms | 1.75ms |
| zen-h2 | 11,301 | 3.02ms | 4.72ms |
| zen-h1 | 4,165 | 7.30ms | 14.58ms |

→ 32 路并发下 h2 每请求约 2ms 排队开销，浏览器常规并发（10–20）下不成瓶颈。

**结论（基线）**：请求速度的"每请求开销"与"下载吞吐"都已经没有可捡的便宜；
真正的用户可见代价只有两处 —— **出站连接重建（§2.1）** 与 **稳定性事件（§5）**。

## 2. 落地的优化

### 2.1 链式出站空闲窗 30s → 180s（请求速度，实测 −211ms/次）

**现象量化**：把 Zen 出站连接池清空后，下一次请求 TTFB 从 205.9ms 升到 **415.7ms**
（+209.8ms = 1 个 RTT：CONNECT 走上游是本地毫秒级，贵的是重放指纹的 TLS 握手）。

**触发频率**：浏览器对同一代理的隧道会保持 5–6 分钟，而 Zen 侧 30s 就丢掉出站连接 ——
"离开标签页半分钟再回来"这种最常见的动作，每次都要为每个目标重付 1 个 RTT。

**改法**：`internal/proxy/upstreamchain.go` 的 `chainedIdleConnTimeout` 从常量改为
`180s`（`ZEN_CHAIN_IDLE_TIMEOUT` 可覆盖，回滚 `=30s` 免重编译）。

**对比实测**（同一条 200ms RTT 合成链路，空闲 35s 后连续 3 次请求）：

| | 首请求 TTFB | 第 2/3 次 |
|---|---|---|
| 改前（30s 空闲窗） | **417.4ms**（冷） | 205.4–205.8ms |
| 改后（180s 空闲窗） | **205.0ms**（热） | 205.6–206.1ms |

→ **每次"回来第一下"省 1 个 RTT（本测量口径 212ms）**；对 200ms RTT 的真实链路≈200ms。

**风险评估**：原 30s 的理由是"上游抖动后别留尸体"，但当时只有归因、没有 A/B 数字。
现在 180s 仍远小于浏览器自身的 5–6 分钟；h2 腿本就有 20s PING 活性检查
（`chainedH2ReadIdleTimeout`），h1 腿有 stock transport 的幂等重试兜底。
未发现新增失败（`fail=0` 全程）。

### 2.2 WebSocket 101 后首帧丢失（稳定性/正确性，红→绿实证）

**根因**：`websocketHandshake` 用 `bufio.Reader` 读完 101 响应后把 reader 丢弃，隧道随后
从裸 `targetConn` 读 —— 后端与 101 同包到达的首帧被读进缓冲区后**永久丢失**。
Socket.IO 的 `0{...}` connect 包、服务端先发型问候帧都属于这一类：客户端等一个永远
不会来的帧（表现为"WS 连上了但卡住/反复重连"）。

**改法**：`internal/proxy/websocket.go` 把残留字节用 `prefixConn` 续在隧道前面
（与 CONNECT 隧道同款处理）。

**红→绿证据**（`internal/proxy/websocket_prefix_test.go`，后端把 101 与首帧写在同一次 Write）：

```
改前：--- FAIL: TestWebsocketBackendPushNotLost (5.02s)
      backend push after 101 was lost; got "HTTP/1.1 101 Switching Protocols\r\n..."
改后：--- PASS: TestWebsocketBackendPushNotLost (0.886s)
```

### 2.3 h2 TTFB 守卫与"刚到的响应体"竞态（防御性修复）

**风险**：`roundTripH2` 的 30s TTFB 守卫在 `RoundTrip` 返回响应头与 `guardTimer.Stop()`
之间若抢先触发，`guardCtx` 已被取消，而响应体正是挂在这个 ctx 上流的 —— 传输会被
中途掐断，`writeResp` 读体出错后按 `http.ErrAbortHandler` 掐掉整条入站连接。
窗口只有微秒级，故**未观测到线上实例**，属防御性修复。

**改法**：`internal/proxy/reoriginate.go` 引入 `guardDone` 原子占位：守卫与成功路径
用 `CompareAndSwap` 争所有权；守卫赢了就把拿到的响应当作 TTFB 超时处理（关闭 body、
改走 h1 镜像腿），**绝不把半死的 body 交给客户端**。

**验证**：既有 h2 回退/镜像测试全绿（`go test ./internal/proxy`），`go vet` 干净。

### 2.4 h2 每目标 transport 换代时回收连接（资源卫生）

`h2TransportFor` 在目标数达 1024 时整表重建，但**没有**对旧 transport 调
`CloseIdleConnections()` —— 旧 transport 的空闲 h2 连接与 readLoop 会一直留到各自的
30s 空闲计时器到期。改为换代前逐个回收。属资源卫生，未声称性能收益。

## 3. 真实网络对比测试

**链路**：生产配置的上游 `http://127.0.0.1:20122`（sing-box）。

| URL | chain-only TTFB p50 | zen TTFB p50 | 差 |
|---|---|---|---|
| `https://www.baidu.com/` | 15.7ms | 15.3ms | −0.4ms |
| `https://www.qq.com/` | 17.6ms | 16.6ms | −1.0ms |
| `cdn.jsdelivr.net/.../jquery.min.js` | 134.2ms | 120.2ms | −14.0ms |

**大文件吞吐（9.14MB，同一 URL）—— 这一项不能用单轮下结论**：

- 第 1 轮四臂：`chain-h2` 28.2、`chain-h1` 27.7、`zen-h2` 9.6、`zen-h1` 9.8 MB/s
- 第 2 轮同四臂：`chain-h2` 48.3、`chain-h1` 49.5、`zen-h2` 11.7、`zen-h1` 11.4 MB/s
- 换一次运行（`ZEN_LEGACY_OUT=1`）：`chain-h2` 9.6→11.1、`chain-h1` 27.1→48.9、`zen-*` 7.5–8.9
- 早前一次运行：`chain` 11.0/11.3、`zen` 48.2/48.5 MB/s（结论**反向**）

→ 同一臂在不同运行之间可从 9.6 摆到 48.9 MB/s（**同臂 5 倍方差**），说明单轮真实网络
A/B 完全被 WAN/节点调度支配。为把"Zen 的处理"与"上游代理本身"解耦，追加受控实验：

**受控实验（本进程中继替代 sing-box，同一 WAN、同一中继实现）**

| 臂 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| relay-only | 4.71 MB/s | 9.08 MB/s | 9.04 MB/s |
| zen-h2 | 4.57 MB/s | 9.25 MB/s | 8.79 MB/s |

→ 逐轮差 −3.0% / +1.9% / −2.8%，**Zen 的数据面在真实 WAN 上与直通中继持平**。
（顺带说明：该 URL 直连 WAN 只有 ~9MB/s，而经 sing-box 可达 48MB/s —— 两条路径根本不是
同一条出口，这本身就是"真实网络测量必须多轮 + 必须解耦"的证据。）

**结论**：真实网络侧能成立的说法只有"TTFB 与直通持平、大文件吞吐无 Zen 归因差异"；
**不能**声称 Zen 让下载更快或更慢 —— 那是 WAN 方差。

## 4. 实测否决的候选（留证据，避免下一轮重复）

### 4.1 入站 h2 `WriteByteTimeout`（"慢客户端占死连接"）
**假设**：客户端不读 → 服务端写阻塞 → 读循环被卡住 → 新流不再派发。
**实测**：构造 h2 客户端（不读、窗口 64KB）请求 16MB，6s 后连接仍在、Zen 未回收；
即使设 `WriteByteTimeout=2s` 也不回收 —— 因为瓶颈是 **h2 流控窗口**（服务端在等
WINDOW_UPDATE，不是等 socket 写），`WriteByteTimeout` 管不到这一层。
**判定**：机制不成立，不落地（`TestPerfSlowClientH2` 保留为机制负证据）。

### 4.2 拷贝缓冲池化（32KB → pooled 64KB）
**假设**：每个响应/隧道现分配 32KB，池化可降 GC 压力。
**实测**：16MB 下载期间堆分配仅 0.01–0.04x 载荷（`io.Copy` 的缓冲在一次拷贝内复用）。
**判定**：收益 <1%，不值得增加共享状态与生命周期风险。

### 4.3 收紧 h2 TTFB 守卫（30s → 10s）
**既有证据**：2026-11-03 凌晨试过（提交 `ca1fc86`），40 分钟后被 `bb9b260` 回滚；
本轮未重复尝试。守卫的真实问题是**阈值大于客户端耐心（Chrome ~15s）**，而不是"太长"；
在 §2.3 修掉竞态后，是否重定阈值应另立测量（需要可控的边缘挂死复现），本轮不动。

### 4.4 "Zen 下载慢 4 倍"（单轮观测）
**实测**：见 §3，同臂跨运行方差达 5 倍，受控实验持平 → **判为测量假象**，不入账。

## 5. 未解问题与下一步（如实登记）

1. **2026-11-03 凌晨的 seek-churn 卡死**（15s 0 字节、关上游链即消失、隔离版无法复刻）：
   本轮仍未定因。已具备的工具：本测量台（合成链路可注入挂死）+ `测试临时\ts_stall_probe\`
   （真 Chrome CDP seek 压测）。下一步应在卡死复现窗口内做并行同刻对比，并抓 Zen 侧
   「出站 CONNECT 阶段耗时 / h2 TTFB 守卫触发 / 入站连接数」三条曲线。
2. **sing-box 交互**：真实网络下 Zen 与直通的吞吐差异不可归因（§3），若用户体感"过 Zen
   比不过 Zen 慢"，需要在 sing-box 侧取证（其 HTTP inbound 的 relay 缓冲/规则匹配），
   不在本仓库可控范围。
3. **引擎每请求 CPU**：本轮复测（`ZEN_AB_RUN=1 BenchmarkAbModifyReq`，3 次 × 35,358 探针 ×
   646,134 条规则）：**85.1 / 108.2 / 112.9 µs/请求**，15.5 次分配、2.3KB/请求
   （复测期间生产 Zen 在跑，取上界；历史值 ~83.8µs）。按 §1 的并发实测它不在用户可感路径上，
   若要继续压请求速度，这是唯一还剩的内部项。

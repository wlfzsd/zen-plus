# 过滤规则核心引擎优化空间研究报告

日期：2026-10-05 ｜ 分支：upstream-chain ｜ 方法：全量代码走查 + 官方 benchmark + CPU profile + A/B 原型实测（含等价性对拍与 20 万条模糊测试）

---

## 一、研究范围与问题

**问题**：过滤规则核心引擎（`internal/ruletree` + `internal/networkrules` + `internal/filter` + `internal/hostmatch`）是否存在极大优化空间——执行效率 ≥+20% 且内存占用 ≥-20%？

**基线环境**：本机实测，go1.27.0，i7-250K（18 线程），语料 = easylist.txt + easyprivacy.txt（102,059 条规则行）。

**引擎每请求热路径**（proxy.go:323/539 → filter.HandleRequest → networkrules.ModifyReq）：

```
ModifyReq(req)
 ├─ renderURLWithoutPort（80ns，1 alloc）
 ├─ primaryStore.Get(url)   ← ruleStore.Get
 │   ├─ ruletree.Tree.Get（规则树遍历）
 │   ├─ generic 规则（O(1)）
 │   └─ 【全部正则规则逐条 MatchString 线性扫描】← rulestore.go:60-64
 ├─ filter(...)（新切片）
 ├─ exceptionStore.Get(url)  ← 同构第二棵树 + 第二组正则
 └─ 每条候选规则 ShouldMatchReq（Header.Get ×2、$domain 时 url.Parse(referer) 165ns/次）
```

## 二、实测数据（全部为本机跑出，非推算）

### 2.1 耗时

| 基准 | 结果 | 来源 |
|---|---|---|
| 官方 BenchmarkMatch（树查询，串行） | 3,980 ns/op，196 B/op，6 allocs | `go test -bench ./internal/ruletree` |
| 同上（18 线程并行） | 277.9 ns/op | 同上 |
| ModifyReq 端到端（真实请求+头） | **16.2~17.4 µs/op**，364 B/op，6 allocs | tmp_enginebench 基准 |
| CPU profile 分解 | **regexp.tryBacktrack 77%**；规则树仅 ~17%；其余 ~6% | pprof 实测 |
| 病态正则定位 | 29 条正则中 **6 条 `^https?://.*` 形状占正则耗时 89%**（单条 1.5~4µs，服务 Worker 拦截类规则） | 逐条计时分布测试 |

### 2.2 A/B 原型验证（原型代码存档于 测试临时\enginebench\）

| 实验 | 结果 | 结论 |
|---|---|---|
| 树 getEdge 线性扫描替代 sort.Search | 串行反而变慢、并行 +9% | 根节点边数多，二分仍是最优；**无 20% 空间** |
| 树 Get 根节点预判跳过不可能遍历 | 同上 | 树根字面边几乎覆盖所有 URL 字符，预判跳不掉；**无空间** |
| trigram 必需字面量预过滤正则 | 3 版实现全部**慢于**朴素扫描 | Go regexp 单次失败匹配仅 ~9ns，已是地板；外层预过滤无利可图 |
| **病态形状特化匹配器**（AST 解析 → 精确等价的字面量/字符类扫描器） | 正则存储 **13.0µs → 3.97µs（-69.5%）**；2 万真实 URL + 20 万随机 URL 对拍 **0 差异** | **有效，远超 20% 门槛** |
| 端到端投影（组件实测加权：regexp 77%×(-69.5%) + 树 17% 不变） | ModifyReq ≈ 17.4 → **~8.1 µs（-53%）** | 引擎热路径效率提升 50%+ 可达 |

### 2.3 内存（live，GC 后）

| 测量 | 结果 |
|---|---|
| 规则树 tree[string] | 29.0 MB / 102,059 行 = **298 B/行** |
| 完整规则引擎（tree + *rule.Rule 对象） | 40.8 MB / 102,059 规则 = **419 B/规则** |
| 外推生产（54.5 万唯一网络规则） | ≈ 228 MB（真实订阅 modifier 更多，实际只会更高）——与《内存优化方案评估报告》推算的 live ~380MB 自洽 |

**内存优化点穷举**（结构性，均需改引擎数据结构）：

| 优化点 | 预估节省 | 侵入性 |
|---|---|---|
| Rule 结构瘦身（无 modifier 规则占 85%+，4 个切片头 96B → 1 个惰性指针 8B） | 引擎 live 的 ~15-20% | 高（触所有 modifier 代码路径） |
| prefix []token（2B/字符）→ ASCII 单字节打包 | ~3-6% | 高（遍历逻辑重写） |
| 节点打包（wildcard/separator/anchor 3 指针 → 1 指针+标志位） | ~2-3% | 中高 |
| 单叶节点内联（leaf []T → 首元素内联） | ~5% | 中高 |
| RawRule 字符串池化 | ~3-4% | 中 |

**结论：单项无一达 20%；全部叠加（乐观）≈ 20-25%，但属于引擎存储层重写级工程**，且引擎内存只占进程总内存的一部分（GC 参数已调优、总占用还有运行时/连接池/证书缓存），折算到进程总占用仅 ~10-15%。

## 三、结论

1. **执行效率：是，有极大空间（实测超门槛 2.5 倍）**。
   瓶颈不在规则树（上游已优化到位，原型证明树侧只剩 <10%），而在 `ruleStore.Get` 对**全部正则规则逐条全 URL 回溯匹配**（占每请求引擎耗时 77%；easylist 系订阅自带的 6 条服务 Worker 类正则是元凶）。
   **解法已原型验证**：在 ParseRule 时对 `^https?://` + `.*` + 字面量/字符类交替 这一类形状做 AST 特化，生成精确等价的快速匹配器（不认识形状的回落到原 regexp），正则存储层 **-69.5%**，引擎热路径预计 **-50%±**。等价性证据：2 万真实 URL + 20 万模糊 URL 零差异。
   工程量：parse.go/rulestore.go 内新增特化器 ~200-300 行 + 形状白名单模糊测试，约 1-2 天，风险可控（识别不了就回落，语义不变）。
2. **内存：否（安全改动无解，激进重构勉强擦线且不划算）**。
   引擎 live ≈ 419 B/规则，唯一大杠杆是 Rule 结构瘦身（~15-20%），叠加其余只有重写级工程才能摸到 20%，折算到进程总占用 ~10-15%；远不如已验证的订阅裁剪（删 AdGuard Spyware 一张 -29.6 万条）。mmap/磁盘驻留维持原判：拒绝。
3. **诚实边界（规则7）**：上述效率收益是"引擎单请求 CPU"口径（组件实测加权），未做端到端接线实测；且该引擎在本应用负载下不构成瓶颈（16µs/请求 × 典型流量 ≈ 不足 1% 单核），用户可感知收益≈0，价值在于高吞吐场景与未来规则量增长。内存侧 20% 目标在引擎内**不现实**，维持上一报告的结论：总量下探靠订阅裁剪。

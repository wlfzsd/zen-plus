## 1. 五类分储（结构核心）

装载期把每条 pattern 归类（判定式，无特判——按 token 构成）：

```
HOSTSET  ||host^                     → map[host][]rule          (24.3万, O(标签数) 查找)
LITERAL  无*无^无|无|| 的其余        → AC 自动机                (24万,  单遍)
SEG      含 * 或 ^（无 ||/| 前导锚）  → 段表 + AC 复用           (0.5万→1.5万段)
REGEX    /…/                         → 现行 token 索引 + WS1 门控 (408, 已验证)
ANCHOR   |http…、||host/path… 等余量 → 保留一台精简 trie        (≈4.3万)
GENERIC  无 pattern                  → 现行 generic 槽（不变）
```

**关键决策：trie 从"万物容器"降级为 ANCHOR 专用**——其规模从 82 万节点 → ~4.3 万模式（≈8 万节点），走位成本与内存同步塌缩。

## 2. 匹配管线（单遍，替代逐位枚举）

```
请求 → matchURL（不变，4096 截断）
  ① 预计算 marker 位图（一次扫 URL，标记分隔符位——原 isTraversalMarker 语义）
  ② AC 自动机单遍扫 URL：
       - LITERAL 命中 → 记 (pattern, 位置)
       - SEG 段命中   → 段位置入该 pattern 的段追踪器
     首次实现对每个 URL 只分配一个复用扫描器（零每请求分配目标）
  ③ HOSTSET：host 后缀链查表（方案 A 已证精确等价，0 误候选）
  ④ SEG 完成判定：各段位置满足 有序递增 + ^段=单分隔符字符 → 候选
  ⑤ ANCHOR trie：仅对锚定小类走位（4.3万条，成本可控）
  ⑥ REGEX：现行 token 索引 + $domain 门控（WS1 原样）
  ⑦ 候选归并 → 修饰符过滤（现行 ShouldMatchReqNav/Res，不动）
```

**通配枚举为何消失**：`a*b^c` 不再枚举 b 的所有位置——AC 找到 a/b/c 各自全部出现位置后，判定"存在递增序列且 b、c 间恰一分隔符字符"是 O(命中数) 的线性归并。位置枚举 O(n²)→线性。

**无损保证结构**：AC/HOSTSET/段表全部是**候选超集生成器**；对超集内每条候选，保留原模式语义的**精确复核**（段序列逐段回放 / 原树单模式复核）——漏选被复核兜底不存在（超集定义），错选被复核剔除。错配率=0 由结构保证而非测试凑数。

## 4. 保序设计（最大风险点，单列攻关）

现引擎候选顺序 = 树 DFS 序。v2 单遍扫描的天然序 = (首命中位置, 模式序)。**两者不等**，黄金 dump（序列哈希）必然改变——这不是可绕过的工程细节，是语义决策点：

- **可保**：block/redirect 决策、applied 多重集（本会话已建立 blockDiff/redirectDiff/multisetDiff 三分离探针方法论，方案 A 实测 blockDiff=0 可达）
- **不可保**：applied 序列逐位一致（树 DFS 序无法从扁平结构复现——方案 A 已实证）
- **方案**：dump 基线重定 + 三重行为等价门禁（①逐请求 block/redirect 恒等 ②applied 多重集对称差=0 ③133,212 请求×4 变体全量差分）+ 赢家翻转影响面专项审计（$badfilter/$removeparam 与 block 规则的竞争序——对每对共存命中做决策不变性证明）
- **这是"新引擎"相对"补丁"的本质代价**，也是它只能作为 v2 独立版本而非热替换的原因

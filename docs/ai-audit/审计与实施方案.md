## 3. 方案一（WS1）：`$domain` 门控正则预筛 —— 已实现并验证

### 3.1 可靠性论证（为什么无损）

1. **`$domain` 是强制条件**：`rule.ParseModifiers` 中 `case "domain","from":` **不设 `isOr`**（`rule/rule.go:308-311`），故落入 `mods.and`（`rule.go:351-354`）。`ModifiersMatchReq` 先遍历 And 且"全部必须匹配"（`rule.go:557-561`）→ **域条件为假 ⇒ 该规则必被丢弃**。
2. **丢弃点唯一且相同**：`Get` 的产出只经 `filterInPlace` 一处消费 —— `ModifyReq` 用 `ShouldMatchReqNav`（`networkrules.go:144`）、`ModifyRes` 用 `ShouldMatchRes`（`:316`）。二者最终都走 `ModifiersMatchReq`；B10 已令 `DomainModifier.ShouldMatchRes` = `matchReqSide`（`domain.go:219-224`），**两侧同一谓词**。
3. **顺序不变**：结果顺序被黄金 dump 哈希（`R|RawRule|FilterName` 序列），故实现**保持按下标升序遍历、只跳过"本就不可能存活"的规则**，不做重排。
4. **必要条件的精确性**：`matchHost` 在"列表存在非否定条目"时要求**某个非否定条目命中**（`permitted || !hasPermitted`，`domain.go:237-263`）；纯字面条目命中 ⟺ `host == 条目 || HasSuffix(host, "."+条目)`（`domain.go:352-355`）→ **"host 后缀链 ∩ 字面条目集 ≠ ∅"是必要条件**。
5. **保守回退**：正则条目、`example.*` TLD 条目、全否定列表、无 `$domain` → **一律视为"恒可命中"**（`alwaysElig`），绝不误剪。
6. **`eff` 语义与 `matchReqSide` 逐行对齐**：Referer 主机名，缺 Referer 时回退目标主机名；Referer 存在但不可解析时 `matchReqSide` 对所有规则返回 false → 门控下"仅 alwaysElig 存活"。

## 4. 方案二（WS2）：锚定位置预筛（`HasSuffix` / `HasPrefix`）

### 4.1 实测剪枝力（现行 `Contains` 对照）

现行 token 索引一律用 `strings.Contains`，对"端锚定字面量"剪枝力极弱甚至为零：

| 规则 | 现行 token / 跳过率 | 端锚定检查 | 端锚定跳过率 | 可省 |
|---|---|---|---|---|
| `i=312` `/^http.*[^?]\?$/` | `"http"`（locked）/ **0%** | `HasSuffix("?")` | **100.0%**（11/33,303 命中） | 68.7 ms |
| `i=357` `/^(\S+\.)?g[1-4][0-9]{8,9}\.com?$/` | `"co"` / 20.8% | `HasSuffix(".co"\|".com")` | **100.0%**（3 命中） | 50.7 ms |
| `i=349` `/^(\S+\.)?[0-9a-f]{15,}\.com$/` | `".com"` / 23.5% | `HasSuffix(".com")` | **100.0%**（2 命中） | 35.0 ms |
| `i=330` `/^(\S+\.)?ad(s?[\d]+\|m\|s)?\.[0-9\-a-z]+\./$`（`$denyallow`） | `"/"` / **0%** | `HasSuffix("./")` | ≥99.1%（306 命中） | 24.2 ms |
| **小计（非域门控，WS1 未覆盖）** | | | | **≈178.6 ms** |

折算：178.6 / 1060.7 = 正则桶的 **16.8%** ⇒ ModifyReq 的 **5–6%**（另加省下的 token 确认开销）。
（`i=142` `/[a-z0-9]{8,}.[a-z]{3,}/` 79.1%、`i=120` `/[0-9]{5}/` 42.3% 亦可端锚定/连续数字预筛，但**二者均有 `$domain` 门控**，已由 WS1 覆盖，不重复计。）

### 4.2 设计

1. `segmentsOfNode`（`tokenindex.go:77`）当前只产出 `locked`（定起点）。**新增 `atEnd`**：某字面段之后的所有 concat 兄弟节点均为零宽（`OpEndText`/`OpEmptyMatch`/`OpBeginText`）时置真 ⇒ 该段必须**恰好落在 URL 末尾**。
2. `reIdx.tokensOf` 由 `[]string` 升级为携带判定方式的结构（`{tok string; kind contains|hasSuffix|hasPrefix}`）；`markCandidates` 的 k-gram 桶保持（k-gram 是必要条件，仍然成立），**确认阶段**改用对应谓词。
3. **可选字面量需做后缀集合展开**：`\.com?$` 的必需后缀是 `{".co", ".com"}`（`"x.com"` 不以 `".co"` 结尾），可复用 `fastshape.go` 已有的"可选组叉乘成多种拼写"机制，上限 16 种拼写，超出即回退 `Contains`。
4. **`HasPrefix` 价值低**：`^` 锚定的前导字面量通常是 `http`（每条 URL 都有，`locked`），剪枝力为零；仅当 `^` 后紧跟非常见字面量时才有意义——按同机制顺带支持即可，不作为收益来源。
5. **保守回退**：无法证明端锚定/前缀锚定 → 退回 `Contains`（零风险）。

## 5. 方案三（WS3）：`altTokens` 分支修复 —— 降级

### 5.1 诊断结果

`altTokens` 在 361 条中返回 nil 的有 321 条，其中 **303 条是"根本没有强制 alternation"**（正常，非缺陷）。真正"有强制 alternation 却被整体放弃"的只有 **13 条 / 107.38 ms**。

根因（`tokenindex.go:166-181` + `branchOneOf:204-217`）：`branchOneOf` 要求分支段 `len(sg) >= idxMinTokenLen(2)`，**任一分支不满足即 `return nil` 放弃整个 any-of 集合**。典型：`(php|jx|jsx|1ph|jsf|jz|jsm|j$)` 的 `j$` 分支只有 1 字节 `"j"` ⇒ 整组作废。而外层本可用紧邻的强制字面量 `.` 折叠成 `.j`（`altTokens` 的 `prefix` 折叠发生在**外层**，救不了内层已放弃的分支）。

### 5.2 为何降级

那 13 条里最大两条（`php|jx|…`，58.72 + 44.47 = **103.19 ms**）**同时是 `$domain` 门控 0 命中规则**，WS1 已把它们整条剪掉。修复 `altTokens` 后，WS1 之外**边际价值仅 ≈4 ms**。

→ **建议：不在 WS1 同批实施**。若将来 WS1 因故不落地，再单独做此修复（修法：`branchOneOf` 允许短段，把长度校验上移到 `altTokens` 折叠 `prefix` 之后）。

## 8. 风险、边界与未解清单

**风险**
1. `effHosts` 每次 `Get` 多一次 512 B 位图清零 + 后缀链 map 查表（约数百 ns/请求）；实测分配持平、净收益远大于开销。
2. `GetHosts` 的 `eff` 若被误传 `nil`，等价于**关闭门控**（回到旧行为）——这是刻意的安全默认，但也意味着"忘了传"只会损失性能、不会出错。
3. 极端 Referer 形态（存在但不可解析）走"仅 alwaysElig"分支，与 `matchReqSide` 语义一致；已纳入性质断言的 3 种请求形态覆盖。
4. `len(s.regexp) > idxMaxRules(4096)` 的未索引回退分支**不启用门控**（保守，仍无损）。

**边界（实测口径限制）**
1. 域 0 命中率（185/194）来自 `urls.txt` 单语料、且**无 Referer**（故 `refHost==ownHost`）。生产中 Referer 普遍存在，那些域表多为小众站点（swiftload.io / biqle.ru / kinos.to 等），命中率只会更低——**方向确定，具体倍数需在生产画像复核**。
2. `matchTime=1060.70 ms` 含 `time.Now()` 插桩开销（每 URL 89 次），是**上界**；pprof 口径（32.75%）与之独立互证。
3. WS2 的 178.6 ms 是按"每规则实测 µs/次 × 可省次数"折算，**未实装验证**。
4. 本次未跑生产稳态画像；WS1 的"live 收益"目前是引擎口径实测 + 基准 A/B，**部署后需 `ZEN_PPROF=1`（127.0.0.1:6399）同 uptime 采点复核**。

**未解清单**
1. 工作树 5 个被删文件（§1）归属未定谳，需用户裁决是否恢复。
2. 生产环境域命中率实测（决定 WS1 的实际幅度）。
3. `filterInPlace` 20.87% 的进一步压缩（§6.1 两个候选，未实测）。
4. 全仓测试的偶发 flaky：`internal/asset/scriptlet` 在全仓并发跑时失败过一次（7.789s），单独跑 0.037s 通过、复跑全仓亦通过；该包 `go list -deps` 不含 networkrules ⇒ **与本次改动无关**，但作为存量 flaky 留痕。

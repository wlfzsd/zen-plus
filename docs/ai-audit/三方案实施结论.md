## 方案 A：实施过程与三个关键发现

**实现**：`pureHostPattern` 判定 `||host^` 精确形态 → `hostRules map[string][]T`（hostMu 读写锁，兼容 liveExc 运行期插入）→ `GetHosts` 按 GetLP 逐字镜像的访问点（hostStart + host 内点）做后缀查表。默认 OFF：`WithHostSplit(bool)` 选项 + `ZEN_AI_HOSTMAP=1` 环境默认。

**发现 1（真实 bug，已修）**：`applyCoverageDedup` 用 `tree.PruneValues` 物理剪枝被覆盖规则——哈希表里的规则够不到，导致父/子域覆盖对**方向翻转**（子域规则该剪的存活）。等价探针第一轮抓到（违规 1699）。修复：新增 `ruleStore.pruneValues` 统一剪树+哈希表，coveragededup 改走它（违规降到 1580，且确认两边存活集一致）。**这条修复对任何未来启用都是必需的。**

**发现 2（语义边界，实证）**：等价探针细化分类后（33,303 URL）：`blockDiff=0, redirectDiff=0, appliedMultisetDiff=1580`。即**拦截/重定向决策 100% 一致**，差异全部是"多条规则同判时，应用循环取第一条，谁被记录为赢家"的翻转——树 DFS 序中 A1 叶与非 A1 叶交错，哈希表**原理上无法**复现原序列 → 黄金 dump 基线必然改变。

**发现 3（性能否定）**：off 3,536ms vs on 3,579ms——树走法成本主要在 root 子树的位置枚举（F 类 24 万条 contains 模式），A1 抽出不削减该成本；候选减少的收益被 hostMu 锁与查表开销抵消。

**裁决建议**：不启用（收益 ≈0 + 赢家报告变化）。代码保留默认关（已证关=位等价），留作研究记录；`pruneValues` 消费者修复**无论是否启用都建议保留**（它同时是未来任何树外索引的正确性前提）。

## 方案 B：上界实测否定（未实施）

**为什么没做**：方案 A 教训（抽叶不削走位成本）在本会话内先做了**收益上界探针**——构建"F 类全部不入树"的有损引擎计时对比（`zz_ai_nof_probe_test.go`，env `ZEN_AI_NOF_PROBE=1`）：

```
off = 3516ms (kept=793,419)
on  = 3513ms (kept=458,920, 跳过F类=337,683)
方案B节省上界 = 0.1%
```

**机制结论**：树走位成本由 marker 位 visit 的结构固定成本主导（visit 调用 + P6 memo/acc 逻辑），与 F 类 24 万条规则几乎无关（去掉后仅省 0.1%）——此前"位置枚举是大头"的推断**被实测推翻**。AC 自动机即使完美实现且保序，收益空间也只有 0.1%，实施（400+ 行核心匹配代码 + 标记对齐 + 归并）完全不成比例。**在写第一行实现代码前被否定，符合"推算≠交付"纪律。**

（原设计要点存档：AC 需标记位对齐回查避免超集误配 `abcxyz.com/tag` vs `xyz.com/tag`；保序靠 (首个标记位, 模式字典序) 归并。仅当未来树机制重构使固定成本消失时才值得重估。）

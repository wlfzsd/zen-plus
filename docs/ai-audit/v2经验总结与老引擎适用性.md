## 一、结构性事实（实测，永久有效——老引擎优化的"地图"）

1. **规则形态学**（572,170 条树模式全分类）：
   A1 `||host^` 46%｜F 纯字面量 45.5%｜A2 `||host/path` 22,864｜A4 15,265｜A3 4,447｜
   D `*` 2,070｜E `^` 204｜B `|http` 35｜C 前导`*` 6｜装饰类 43,931（asset 引擎接管，不进树）。
   → 含义：优化必须按形态分流，一刀切方案必然为少数形态付全量代价。

2. **时间账·未门控**（裁剪探针，基线 3,506ms）：D+E 通配类 53.2%、root 类合计 91.1%、F 37.9%、A 类 ≈0。

3. **时间账·WS1 门控后**（E2 CPU profile，4720ms 采样）：
   树遍历 ~40%（traversePrefix 20% + exception 11% + wildcardTail 7% + getEdge 4.7%）｜
   regex 回溯 11.4%｜MatchDomain 8.5%｜map 哈希类 12.5%（memHashAES+matchH2+mapaccess）。
   → 含义：无单一 20%+ 热点；树遍历是核心工作本身。

4. **内存账**（live 135.5 → hostSplit 后 130.7MB；abbench 口径）：
   树 82.7（64B 节点×80万=51MB + 边 12.8 + arena 11.2 + 叶 4）｜文本 35.5｜规则对象 50｜正则 5。
   RSS 320 = live + **173MB span 混合碎片**（实测 FreeOSMemory 无效、文本 arena 搬迁零返还）。

5. **树的密度事实**：64B size class 精确、1B/token arena（1c）、trimslice 精确裁剪、公共前缀大量共享
   （A1 24.3 万条仅占 ~25MB 树份额）——**树已近地板，"搬空某类小对象"解不出 span**。

6. **两线成本的本质约束**（v2 的核心发现）：
   - CPU：**段归并成本 ≈ 它替代的枚举成本**（map-AC 归并/扫描比 18:1 → DAT 复现 +22.3%）——"消除枚举"换不来净胜
   - 内存：**新结构固定成本（数组+文本+元数据 45-60MB）＞ 树份额节省（25-27MB）**——替换式结构内存必负

## 四、待办的真实增量（按收益排序，全部已定稿可直接实施）

1. **T1：树侧 $domain 门控索引化（WS1 第二期）——−5~7% CPU**
   事实：regexp 库门控已是反向索引（tokenindex.go:49-61 `byDomainRef/byDomainAny`+`alwaysElig` 位图），
   但**树候选的 $domain 仍逐候选全量比对**（ModifyReq → ShouldMatchReqNav → matchReqSide →
   MatchDomain，domain.go:389 逐 entry 后缀比对 + eTLD1Cache RWMutex）——E2 的 8.5% 即此。
   方案：带可索引 $domain 的树规则分配位号；GetHosts 按 eff 后缀链 markEligible 出位图；树候选按位过滤
   （O(1)/候选）。可靠性=WS1 同构（同一必要条件，非可索引门保守放行）。~120 行，门禁现成。
2. MatchDomain 微优化 ≈ T1 子集，不单列。
3. RSS 全堆紧凑化：唯一"大"内存项（320→~180），仅 RSS 口径、v2 级工程——仅当你在意任务管理器数字时立项。
4. 其余零碎 ~3-5%。

## 五、过程教训（v2 为什么失败——流程级，防重蹈）

1. **选型前没算成本账**：新旧每字节/每请求成本一页纸对比即可否决 DAT 内存线——这笔账到 428.9MB 实测爆了才第一次算。
2. **只原型了一个方案**：map-AC spike 已给出 18:1 归并/扫描警报，被当成实现问题而非架构问题。
3. **警报未触发回炉**：S3'（+22.8%）+ 自记"收益上限被 53.1% 封顶、风险收益比不佳"，仍按原方案冲。
4. **6 轮补丁循环**：merged 父链→depth 公式→trie 假边→空槽链→T4a 编码→v 参数——每轮都当实现 bug 修，违反"连续失败换思路"。
5. **估算三次被实测打脸**：Parsed 150MB→实际 34MB；文本 arena 25MB→0.7MB；树打包 20MB→2MB——**估算必须先用代码实读校准**。
6. **正确流程（下次照此）**：理论账 → ≥3 个并行 spike → oracle 对拍 → 数据选型 → 每轮失败先问方案再问 bug。

## 六、对老引擎的最终判断

- 匹配结构已到实测地板（多轮遗产叠加）；"可替代部件"经 9 轮逐项盘点不存在有意义收益。

- 语义不变前提下，"大幅提升"窗口已关闭——这是测量结论，不是懈怠；若要突破需改语义或减规则（不可接受）。
